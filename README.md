仕様の正本、重要な設計判断、判断時点の根拠を残す。コードの逐語訳や作業日誌を増やすことは目的にしない。

文書の案内は [index.md](index.md) にまとめる。このファイルは書き手のための運用ルールとする。

| 項目 | 設定 |

| PROJECT | `{{PROJECT}}`。プロジェクトの固定略称。 |

| 担当不在時の引き継ぎ先 | `{{例: プロジェクトの保守担当チーム。後任が決まるまで文書の管理窓口を担当する。}}` |

## 配置

```text
docs/
├─ README.md       # 書き手向け: この運用ルール
├─ index.md        # 読み手向け: 文書の案内
├─ spec/           # 合意する仕様とSPEC雛形（_template.md）
├─ adr/            # 重要な設計判断の履歴とADR雛形（_template.md）
├─ research/       # 独立させる価値がある調査とRESEARCH雛形（_template.md）
├─ glossary/       # 用語集とGLOSSARY雛形（_template.md）
├─ examples/       # 架空の完成例。実プロジェクトの文書とは別枠
└─ scripts/        # 検査スクリプトを直接実行する
   ├─ check-docs.ps1  # Windows PowerShell用
   ├─ check-docs.sh   # Linux / Bash用
   └─ tests/         # 検査器のテスト・共通テストケース
```

各雛形を置く4ディレクトリ以外は、内容が必要になるまで空の実文書や将来用ディレクトリを作らない。

`index.md`には実在する主要文書へのリンクと短い案内だけを置く。
主要文書以外も発見できるよう、リポジトリ検索、閲覧サイトの検索、または自動生成した文書一覧のいずれかを`index.md`から案内する。

全件の状態・更新日・担当者を手動転記した台帳にはせず、その正本は各文書に置く。

## 何を、どこへ書くか

| 文書 | 答える問い | 作成・更新の単位 |
|---|---|---|
| SPEC | 何を保証し、どの条件でどう振る舞うか | 原則1スコープの概要から開始。独立して改訂・参照する契約だけ分割する。 |
| ADR | どの方針を提案し、なぜその判断に至ったか | レビュー可能な具体案から始め、重要で、個別に見直せる判断を1件ずつファイルにまとめる。 |
| RESEARCH | 何を調べ、どこまで確認できたか | ADR内の比較・出典では足りない調査だけ独立させる。 |
| GLOSSARY | このプロジェクトでは何を意味するか | 原則全体で1ファイル。誤解しやすい用語が出たときに作る。 |

雛形: [SPEC](spec/_template.md) / [ADR](adr/_template.md) / [RESEARCH](research/_template.md) / [GLOSSARY](glossary/_template.md)

完成例: [最小のSPEC・ADRと読み方](examples/README.md)。完成例は雛形に混ぜず、記述量と文書間のつながりを確認するときだけ参照する。

## 導入と1コマンド検査

Windowsは標準のWindows PowerShell 5.1以上、LinuxはBash 4以上と`find`・GNU互換の`realpath -m`を使う。
追加のプログラミング言語・モジュール・ライブラリは導入しない。検査はオフラインで動作し、文書を書き換えない。

両実装は同じ検査規則と共通テストケースを使う。汎用的なYAML・Markdownパーサーではなく、下記の対応記法を検査する。

このテンプレート集を検査する場合:

```powershell
.\scripts\check-docs.ps1 -Template
```

```bash
bash ./scripts/check-docs.sh --template
```

導入先へはREADME、index、4種類の雛形、`scripts/`、必要なら`examples/`を`docs/`へコピーする。
`examples/`を省く場合は、このREADMEの完成例への案内も削除する。

同梱の`.gitattributes`もコピーするか、`.sh`のLF・`.ps1`のCRLF指定を既存設定へ取り込む。

READMEのプロジェクト設定とindexを記入したら、**導入先では`-Template` / `--template`を付けない**。

```powershell
.\docs\scripts\check-docs.ps1
```

```bash
bash ./docs/scripts/check-docs.sh
```

検査対象は`scripts/`の親ディレクトリで、作業ディレクトリには依存しない。別の場所はPowerShellの`-Root "文書ディレクトリ"`、Bashの`--root "文書ディレクトリ"`で指定できる。

終了コードは成功`0`、文書の検査エラー`1`、検査器が検出した実行環境等のエラー`2`。文書のエラーには対象ファイルと行番号を表示する。

Windowsの実行ポリシーでスクリプトを実行できない場合は、組織・端末の既存の運用に従う。検査器がポリシーを変更することはない。
プロセス限定の指定が許可されている端末では、`powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-docs.ps1 -Template`でも実行できる。永続的なポリシー設定は変更しない。

CIにも同じコマンドを設定できるが、このテンプレートは特定サービス向けのCI設定を追加しない。

`-Template` / `--template`が許可するのはルートのREADME・indexの未記入欄だけで、実文書の検査は緩めない。
`examples/`の完成例は常に未記入欄を許可せず検査し、文書IDとADRの置換関係は実文書とは別枠で照合する。

検査器を変更した場合は、Windowsで`.\scripts\tests\run-tests.ps1`、Linuxで`bash ./scripts/tests/run-tests.sh`を実行する。
回帰テストは`examples/`を入力に使うため、テストを実行する環境には完成例もコピーする。

仕組みと結果の読み方は、末尾の[付録: 検査器のテスト](#付録-検査器のテスト)を参照する。通常の文書更新では、まず`check-docs`による文書検査を行えばよい。

### 検査器が対応する記法

追加依存なしで同じ規則を再現するため、メタデータは雛形で使う次の記法に限定する。任意のYAML構文を完全に検査するものではない。

- UTF-8の文書を使い、メタデータを行頭の`---`で囲む。キーは1行1項目で、重複させない。
- 文字列は単一行の引用符付き、または`Active`のような英数字・アンダースコア・ハイフン・ピリオドの値。日付は引用符で囲む。
- 配列は`["担当チーム", "別チーム"]`のように、空でない引用符付き文字列を1行に並べる。
- コメントは独立行または値の後の`#`で書く。`null`と`true`は過去記録例外に使う。
- キーは本規約の必須・任意項目に限定する。入れ子は`trace:`の下に半角スペース2個で置く`req: ["上位ID"]`だけに対応する。
- 複数行文字列、引用符のエスケープ、ブロック形式の配列、アンカー・エイリアス、独自タグ・キーなどは対応外としてエラーにする。既存の独自メタデータを使う場合は検査器も拡張する。
- PROJECTとSCOPEは英大文字・数字・アンダースコア、slugは英小文字・数字・ハイフンを使う。
- 相対リンクは`[説明](相対パス)`形式とし、宛先の空白や括弧は`%20`・`%28`・`%29`で表す。画像も同じ宛先規則に従う。参照形式リンクやタイトル付きリンクは対応外としてエラーにする。
- 機械検査する用語表は雛形と同じ、行頭と列区切りに`|`を使う形式とする。SPEC内の表は条件一覧等を読みやすく示すために任意で使う。

対応記法の構文、管理項目、参照関係を機械で確認し、内容の妥当性は後述のチェックリストで人が確認する。

## 正本と参照

SPECは合意する契約、コードとテストは実装・検証の成果物、ADRは判断案と確定した判断・理由、RESEARCHは調査時点の根拠とする。ProposedのADRは未合意であり、現行方針の適用根拠にはしない。
一致しない場合は黙って片方を正とせず、不具合か仕様変更かを判断して追跡する。

OpenAPI、Schema、公開ヘッダー等がある場合は、構造・型の正本を1つ決め、SPECへ複製しない。

長期にわたって参照する判断理由はADR本文に残し、Issue・PRだけに依存させない。

局所的な工夫はコードコメント、局所的な変更理由はPRで足りる。
全ての関数・クラス・依存ライブラリにADRを作る必要はない。

## IDとファイル名

```text
ID:        <PROJECT>-<SCOPE>-<TYPE>-<NNNN>
ファイル名: <doc_id>-<固定slug>.md
```

`TYPE` は `SPEC | ADR | RESEARCH | GLOSSARY`。`NNNN` はPROJECT×SCOPE×TYPEごとの4桁連番で、0001から開始する。

slugは、文書の内容を人が見分けやすくするファイル名末尾の短い識別名とする。例: `event-transport`、`command-contract`。
slugは原則として英小文字・数字・ハイフンで構成する。`<固定slug>`の「固定」は文字列の一部ではなく、作成後に変更しないという意味である。

IDとslugはリンクや外部参照を安定させるため原則固定する。タイトル、日付、版が変わってもファイル名は変えない。欠番を埋めず、番号を再利用しない。
scopeの分類が変わっても既存IDは改名せず、本文の適用範囲や任意の`affects`で説明する。

命名例（`PLCB`、`CORE`は例示。利用時は自分のPROJECT・SCOPEへ置き換える）:

```text
PLCB-CORE-SPEC-0001-overview.md
PLCB-CORE-SPEC-0002-command-contract.md
PLCB-CORE-ADR-0001-event-transport.md
PLCB-CORE-RESEARCH-0001-event-transport.md
PLCB-GLOBAL-GLOSSARY-0001-terms.md
```

採番台帳は初期には設けず、マージ済み文書と進行中PRを確認して次の番号を使う。衝突はマージ前に解消する。

SPECを分割するときは親文書に分割先を案内し、新しい文書に新IDを付ける。統合で役割を終える文書はDeprecatedとし、統合先を案内する。旧文書IDを別の契約へ再利用せず、関連仕様・ADR・indexとテスト側の参照を見直す。

GLOBALは全体構成・全体共通の方針、コンポーネントのSCOPEはその責務内の判断、XCUTは複数コンポーネントを横断する特定の関心事に用いる。
分類に迷う場合は、主担当のスコープに文書を1件だけ置き、影響先を記す。GLOBALとXCUTへ同じ決定を重複させない。

分類名や連番の大小で優先順位は決めない。既存の共通方針への例外は明記し、関係者と整合を取る。

## Front matter

SPEC / ADR / RESEARCH / GLOSSARYの実文書には次の6項目を必須とする。
`index.md`、このREADME、雛形には実文書としてのIDを付けない。

ADRの新しい提案は`status: Proposed`で作成し、`decision_date`と`decision_makers`は省略する。AcceptedまたはRejectedへの確定時に、確定日と判断した人間の担当者・チームを記録する。Superseded・Deprecatedになった後も当時の値を保持する。確定済みの判断を遡及記録する場合は、その判断の現在の状態から作成してよい。

ADRの提案・結論・適用範囲・理由は本文に記載する。

過去の判断を遡及して記録し、判断日または判断主体が不明な場合だけ、`legacy_record: true`と理由を書いた`legacy_note`を必須とし、不明な値を`null`とする。現在の判断にこの例外は使わない。

次はSPECを新規作成する場合の記入例であり、このREADME自身のメタデータではない。

```yaml
---
doc_id: "{{PROJECT}}-{{SCOPE}}-SPEC-{{NNNN}}"
title: "{{対象}}の仕様"
type: spec
status: Draft
owners: ["{{担当者またはチーム}}"]
updated: "{{YYYYMMDD}}"
---
```

`type` は小文字で `spec | adr | research | glossary`。

`owners` には文書の管理窓口となり、内容に責任を持つ人間の担当者・チームを記載し、執筆者全員や承認者を列挙しない。AIやモデル名は記載しない。

`updated` は内容・適用範囲・状態等を最後に更新した日とする。整形だけの変更やビルドのたびには更新しない。

判明している日付はISO 8601基本形式の`YYYYMMDD`とし、文字列として引用符で囲む。雛形の`{{...}}`は実文書へコピーするときに置換する。

任意項目は使うときだけ追加する。空配列や空欄を埋めるための作業はしない。

| 項目 | 用途 |
|---|---|
| `rev` | 独立配布するSPECの契約版。通常は不要。 |
| `trace.req` | 既に存在する上位要件との対応。これだけのためにREQ台帳を作らない。 |
| `supersedes`, `superseded_by` | 置換関係にあるADRのdoc_idの配列。実際の置換時だけ追加する。 |
| `affects` | 採番時のSCOPE以外にも影響する範囲。必要なときだけ指定する。 |
| `legacy_record`, `legacy_note` | 過去のADRを遡及記録し、判断日または判断主体が不明な場合のみ使う。 |

機械処理しないリンクは本文のMarkdown相対リンクを基本とする。全リンクをfront matterへ二重登録しない。
独自の`links`等を既に運用している場合は、参照するツールがある項目だけ維持する。

## AI利用の記録

この規則は、人間の担当者と、文書を作成・更新するAIの両方に適用する。

SPEC / ADR / RESEARCH / GLOSSARYの作成・更新、またはその文書が記録する調査・設計・判断・実装・検証にAIを利用した場合は、対象文書の本文末尾に「AI利用記録」を記載する。

文章の下書き・校正などの補助も対象とし、AIが開発や判断案の作成を主導した場合は、その役割を明記する。文書作成時にAIを使わなくても、記録対象の判断等にAIが関与した場合は省略しない。

- 記録する項目は、利用日、提供元・モデル名、関与した範囲、役割・利用内容とする。モデルの版や識別子が確認できる場合は併記する。

- ツール名・サービス名だけでモデル名の代わりにしない。モデル名や版を確認できない場合は「不明」とし、確認できたツール名等と不明な理由を記す。AI自身も、利用環境から確認できないモデル名・版を推測して記入しない。

- 複数モデルを使った場合は、モデルごとに範囲と役割を分けて記す。同じ日・モデル・役割の作業はまとめてよく、全プロンプトや会話ログの転記は不要とする。

- AIが対象文書を作成・更新する際は、自分の関与も記録する。他のAIの関与は確認できた事実だけを記載し、未確認の利用履歴を作らない。

- AIの関与の程度にかかわらず、内容の確認と採用に対する責任は`owners`の人間側にある。ADRの`decision_makers`には判断を確定した人間の担当者・チームを記し、AIによる比較・推奨・判断案は「AI利用記録」に分ける。人間による確認・合意をAIが推測して記録しない。

- 更新時は、追加のAI利用を記録する。過去の判断時点のモデル・役割を、今回使ったモデルで上書きしない。AI未使用なら節を省略してよいが、既存の利用記録は今回未使用でも残す。

記入形式（各雛形の同名の節を使う。新しいfront matter項目は追加しない）:

```markdown
## AI利用記録

| 利用日 | 提供元・モデル名（確認できる版・識別子） | 関与した範囲 | 役割・利用内容 |
|---|---|---|---|
| {{YYYYMMDD}} | {{提供元・モデル名}} | {{文書・節・振る舞い・判断・実装等}} | {{下書き、校正、調査、比較・推奨、実装、検証等。主導した場合は明記}} |
```

この記録はAIの関与を示すものであり、技術的な主張の根拠や検証結果の代わりにはしない。一次資料や実測結果は通常どおり本文から参照する。

利用の有無、モデル名の正確さ、記録の十分さはレビューで確認する。検査スクリプトはAIの利用実態を判定しない。

## 状態

### SPEC（type: spec）

| 状態 | 意味 |
|---|---|
| `Draft` | 検討中の仕様。 |
| `Active` | 合意済みで、適用対象となる仕様。 |
| `Deprecated` | 新規利用を止めた仕様。 |

`Active`のSPECには、契約となる振る舞い・保証・適用範囲を確定できない未決事項を残さない。そのような論点がある間は`Draft`とする。

`Active`は実装完了を意味しない。実装進捗はIssue・PRで追跡し、SPECには対象リリースと未反映の重要な差分だけを示す。

### ADR（type: adr）

ADRの`status`は、記載された提案への合意と判断の現在の有効性を表す。

| 状態 | 意味 |
|---|---|
| `Proposed` | 具体的な方針・理由・影響をレビューできるが、まだ合意していない提案。 |
| `Accepted` | ADRに書かれた判断に合意済みで、現在有効な判断。 |
| `Rejected` | 提案を審議し、却下した記録。 |
| `Superseded` | 後継ADRに置き換えられた判断。 |
| `Deprecated` | 後継なしで適用を終了した判断。 |

`Accepted`には、不導入・延期・現状維持の方針への合意も含む。現行方針は`Accepted`のADRで確認する。`Rejected`は却下した提案の記録であり、現在の適用方針ではない。

`Accepted`は実装完了を意味しない。実装進捗はIssue・PRで追跡する。

`Deprecated`を「非推奨だがまだ有効」の意味では使わない。

代替案の扱いには`Selected | Dismissed | OutOfScope`を使う。`Proposed`では暫定評価であることを明記し、未評価の候補は未評価と記す。

### RESEARCH（type: research）

| 状態 | 意味 |
|---|---|
| `Draft` | 調査中の記録。 |
| `Complete` | 対象範囲内の調査を整理済みの記録。 |
| `Archived` | 現在の判断の直接根拠としては使わない記録。 |

`Complete`は採用承認や内容の永続的な正しさを意味しない。

### GLOSSARY（type: glossary）

| 状態 | 意味 |
|---|---|
| `Draft` | 検討中の定義集。 |
| `Active` | 現在の定義集。 |
| `Deprecated` | 廃止した定義集。 |

この状態は用語集全体に適用する。個々の用語の現行・廃止は用語表の状態で管理し、一部の用語を廃止するだけで文書全体を`Deprecated`にしない。

## 判断の履歴

通常の変更は、可能なら仕様・実装・テストを同じPRで更新する。
設計を先行させる場合は対象リリースと実装の追跡先を示す。

ADRは合意を求められる具体案ができた時点でProposedとして作成する。Issue・PRでは質問・反論・実験・作業を追跡し、ADRには現時点の提案・判断基準・代替案・想定する影響をまとめる。独立させる価値がある調査はRESEARCHに記録する。

1本のADRは一つの検討課題と判断案・結論を記録する。採用しなかった候補ごとにRejectedのADRを作らず、通常は合意したADRの代替案に理由を残す。ADRとして提案した方針自体を却下した場合はRejectedとし、提案内容と却下理由を残す。

Proposedの間は提案・理由・適用範囲をレビューに応じて編集できる。変更の経緯はIssue・PRやGitの差分で追跡する。確定時には未決事項を解消し、状態・判断日・判断者・本文を揃える。

Proposedは原則として未マージのPRで共有する。審議前に取り下げる場合は、理由を付けてPRを閉じ、IssueにPRと当該コミットへの参照を残す。取り下げをRejectedと扱わず、IDも再利用しない。

```text
Proposed → Accepted
Proposed → Rejected
Accepted → Superseded（後継ADRに置換）
Accepted → Deprecated（後継なしで廃止）
```

判断の確定後も、誤記、リンク、状態、日付付きの観測結果は修正・追記できる。
ただし当時の結論や採否の理由を別の内容に上書きしない。意味・適用範囲を実質的に変えるときは新ADRにする。

Acceptedの判断を覆すときは後継ADRを作り、旧ADRをSupersededとする。Rejectedの提案を再検討するときは新しいIDで提案し、旧ADRへ本文でリンクする。旧ADRはRejectedのまま保持し、置換関係にはしない。

意味を変えない説明の補足は追記し、実質的な変更は後継ADRで表す。

後継となる判断の検討中は、旧ADRをAcceptedのままにする。Proposedの新ADRから旧ADRへ本文でリンクし、置換予定を示す。ProposedとRejectedには`supersedes`・`superseded_by`を設定しない。

後継ADRをAcceptedにするPRで、新側の`supersedes`、旧側の`superseded_by`とSuperseded状態、関連するSPECの参照を整える。成立した置換関係は、後継ADRがさらにSuperseded・Deprecatedとなった後も履歴として保持する。

移行の完了前なら適用時期と移行Issueを示す。旧判断が一部残る場合は、その範囲を後継ADRに明記する。

Rejected・Superseded・DeprecatedのADRは削除しない。却下理由や当時の制約も履歴として残す。Deprecatedとする場合は、本文に廃止日と適用を終了した理由を追記する。

RESEARCHは、後から測定値を差し替えて過去の根拠を変えない。Complete後に結論が変わる追試は新しいRESEARCHに分け、旧文書が現在の判断の直接根拠でなくなればArchivedとする。同じ文書への追記は、結論を変えない補強、誤記の訂正、または日付と条件を分けた観測に限る。

ADRからRESEARCHを判断根拠として参照するときは、通常の相対リンクに加え、対象コミットまたは不変の公開版も示す。

## SPECの構成と書き分け

SPECは、機能・責務ごとの振る舞いを文章で直接規定する契約（contract）とする。目的と範囲を示したうえで、読み手が利用の流れや条件を追えるように説明する。F/Nの要件ID、要件ごとの状態、固定アンカーは設けず、安定した文書IDと文書単位の参照を使う。

基本の構成は次のとおりとし、見出し名や節の分け方は対象に合わせる。短い内容は段落にまとめ、不要な節や将来用の空欄を増やさない。

| 内容 | 書くこと |
|---|---|
| 目的と範囲 | 利用者、課題、得られる結果、担う責務、適用先・前提、対象外、未実装・移行中の重要な差分。 |
| 関連仕様 | 他のSPECやスキーマとの責務分担、依存する契約、正本の参照先。 |
| 機能・振る舞い | 対象に合う節で、開始条件、入力、処理規則、出力、状態、失敗時の扱い、副作用、保証しないことを定める。 |
| 共通制約（必要な場合） | 複数機能にまたがる規則と適用範囲・例外。 |
| 設計判断・関連資料 | 現行方針の理由とADR、実装・運用等の関連資料。 |
| 未決事項 | 未確定の論点と仕様の確定への影響。なければ「なし」とする。 |

構造・型の正本がOpenAPI、Schema、公開ヘッダー等にある場合は参照し、定義を複製しない。対象外の説明では、製品として保証しないもの、別SPECで定めるもの、未採用・将来検討の候補を区別する。対象版・ブランチは適用先を区別する必要があるときに具体化し、構成整理のためだけに版区分を新設しない。

### overviewと個別SPECの分担

overviewは、全体の目的・責務・処理の流れ・文書間の関係と、全体に適用する横断的な契約を記す。個別SPECが定める入力形式や振る舞いの定義は重複記載せず、文書へのリンクとその役割を示す。単なるリンク集にはせず、全体として何を保証し、各責務がどうつながるかを説明する。

個別SPECは担当する機能・責務の契約を定める。関連仕様には参照先の文書IDを示し、相対リンクを添える。独立して参照・改訂する必要が生じるまでは一つのSPECでよく、overview専用の雛形や文書を形式的に追加しない。indexは読み手の案内にとどめ、overviewの説明を複製しない。

### 機能のまとめ方と追記

- 利用者の目的・操作、またはまとまった責務で見出しを作り、利用の流れや意味の近さで並べる。関数・クラスごとには分けず、追記は該当する振る舞いの説明へ入れる。
- 主体・成立条件・求める振る舞いを明確にし、正常時、不正入力時、状態変化、失敗・キャンセル時の結果をつながりのある文章で定める。「適切に」「速やかに」等の測定不能な表現だけで保証を済ませない。
- 条件一覧、入出力の対応、状態遷移等は、その説明の中で局所的な表を使ってよい。表への一括登録を必須にせず、文章と表で同じ保証を重複定義しない。契約は本文全体で表し、別の「受け入れ確認」へ再掲しない。
- 複数機能が共有するデータ保護、認証・認可、性能・運用条件等は一か所に定め、適用する機能と例外を示す。特定機能だけに適用する制約はその機能の説明に置く。性能等の保証には、負荷・測定区間・集計方法・閾値など意味を確定する条件も含める。
- 内部設計の補足や運用手順は必要な場合だけ添え、参考情報・作業手順と契約を区別する。コードの逐語訳や全クラスの説明は書かない。契約を検証する具体的な手順・ケースはテスト側で管理する。

### 既存SPECを移すとき

1. 現在の文章と表から、適用範囲、成立条件、正常・異常時の保証、例外、未決事項を確認する。文書ID・slug・Front matterと文書全体の状態は維持する。
2. 要件表にあった保証を、対応する機能・責務の文章へ移し、既存の詳細と統合する。受け入れ基準にだけ書かれていた条件も確認し、契約の一部なら本文へ残す。単に表を削除して保証を失わない。
3. F/Nの識別子と行の状態管理を外す。旧IDからの参照を探し、SPEC文書IDと対象の振る舞いの説明による参照へ更新する。廃止済みの内容を現行の契約へ戻さず、利用者に必要な廃止・移行の説明は文章で残す。
4. 検証手順・ケース・実行結果はテスト側へ移す。まだテストがなければ既存のIssue・実装計画で追跡し、SPECにテスト一覧や架空のリンクを作らない。
5. 変更前後で保証の欠落・重複、共通制約の適用先、関連文書とテスト側の参照、未決事項を照合する。保証の追加・意味の変更は構成整理と区別し、構成の変更だけで実装済み・合意済み・検証済みと扱わない。

## SPECとテストの対応

契約を検証するテストファイルまたはスイートから、関連するSPECの文書IDを参照する。例えばCLIの契約テスト群に`DEMO-GLOBAL-SPEC-0001`を記し、個々のテストは「不正な引数なら標準エラーに通知して終了コード2を返す」のように、条件と期待する振る舞いが分かる名前にする。コメントや既存のテスト記述の中で参照できればよく、専用の台帳や新しいメタデータ形式は設けない。

参照はテスト側からSPECへの一方向とする。SPEC側にテスト一覧・検証計画・実行結果を重複保持せず、要件IDや固定アンカーも設けない。規定する保証と、その保証を確かめる具体的な手順・ケースは区別する。保証の意味を決める条件はSPECに残し、入力例の組み合わせ、セットアップ、実行方法、期待値との比較はテスト側で管理する。

### テストを作成・更新するとき

契約を観測できる境界とテストの粒度を選ぶ。例えば解析関数の単体テストだけでは、CLIがどの出力先へ書くか、どの終了コードを返すかまでは保証できない。必要な結合テスト・システムテストで実際の呼び出し境界から確認する。内部関数やクラスの実装を支える単体テストすべてに、SPECへの直接参照を要求しない。

SPECを変更するときは文書IDで関連するテスト群を探し、正常系に加えて境界値、不正入力、失敗、状態変化、キャンセル、再試行、副作用等の該当する保証に漏れがないかレビューする。複数SPECにまたがる振る舞いなら、その関係と適用条件も確認する。文書の分割・統合時にはテスト側の参照も見直し、意味が変わっていなければ構成整理だけを理由に期待する振る舞いを変えない。

文書IDの参照があるだけで、そのSPEC全体を検証済みとは扱わない。テストが観測する振る舞いと条件、確認できない範囲、実行結果を見て判断する。現在の文書検査器はテストソース内の文書IDや検証の網羅性を検査しないため、参照先と検証範囲はレビューで確認する。

## 用語の参照

用語IDは用語集内で`T001`等とし、外からは`<doc_id>/T001`で識別する。同じ表記でも意味または適用範囲が異なれば別IDにする。

## 分割・追加の条件

ADRは、外部契約、状態・永続化、セキュリティ、重要な品質特性、長期依存、移行コストに関わる判断や、後から誤って覆されそうな非自明な判断に作る。
短く済む理由はSPECの関連判断節、局所的な理由はコードコメント・PRでよい。

読者や更新のタイミングが異なる場合、個別に参照する必要が生じた場合、または更新の衝突や探しづらさが続く場合に文書を分ける。
行数だけで機械的に分割せず、空の章や将来用ファイルは作らない。

手順書は作業として独立して参照する場合だけ`runbooks/`等に置く。初期にはSPEC内でよい。

## 最小のレビューと検査

PRでは、振る舞いを変えたか、長期にわたって参照する判断理由を残す必要があるか、検証方法があるか、未決事項を隠していないかを確認する。
文書変更が不要な場合はPRに理由を一文記せばよい。

マージ前に、同梱の検査コマンドをCIまたはローカルで実行し、最低限、次の項目を確認する。

- 対応記法に沿ったメタデータの構文、共通の必須項目、ADRの必須項目。
- 過去の判断を記録する際の例外規定との整合性、文書の種類に応じた状態。
- 文書IDの重複、用語集内の用語IDの重複。
- 後継IDの存在、ファイル名の形式、相対リンクの参照先の存在。

各文書ディレクトリ直下の`_template.md`だけを雛形として検査対象外にする。それ以外の実文書は`<doc_id>-<固定slug>.md`の形式とする。

導入後のREADMEと`index.md`、および実文書の可視本文に`{{...}}`が残っていればエラーとする。雛形、HTMLコメント、コードフェンス内の記入例は対象外にする。リンク検査も同様に記入例を除外する。

導入後の`index.md`から案内する主要文書は、原則としてSPECとGLOSSARYはActive、ADRはAccepted、RESEARCHはCompleteとし、リンク先のfront matterも検査する。例外的に他の状態を案内するときは、リンクと同じ行に`（Proposed: レビュー対象のため）`のように実際の状態・コロン・理由を併記する。

外部リンクの一時障害や更新日が古いだけの理由で、初期からマージを止めない。

ADRの置換関係は、存在・相互参照・循環・Superseded状態との整合、Proposed・Rejectedに置換関係がないことも機械検査する。

実文書の走査範囲は`spec/`・`adr/`・`research/`・`glossary/`の配下。ルートのREADME・indexは本文の検査対象とする。

用語IDは用語集の`ID`・`状態`列を持つMarkdown表から読み取り、文書内で重複を検査する。他の用語集の`T001`とは衝突扱いにしない。SPEC内の局所的な表は項目ID・行状態の検査対象にしない。

相対リンクは対応記法のMarkdownリンク・画像の参照先の存在を検査する。HTMLのリンク、URLのアンカーの成立、外部URLの応答、別置きの手順書内部は自動検査の対象外とし、必要な変更時に人が確認する。

文書ID・slugの過去からの不変性、状態遷移の妥当性、本文の提案・結論と状態の整合、例外理由の妥当性、本文と実装の一致は人がレビューする。検査成功だけで合意や内容の正しさを保証しない。

### 変更時のチェックリスト

該当する項目だけをPR本文またはレビュー時に使う。README自体のチェック欄を完了状態に変えず、実行結果の台帳も作らない。

通常の変更:

- [ ] 振る舞い・保証・適用範囲が変わるならSPECを更新し、文書IDで関連テスト群を探して検証範囲とケースを見直した。文書変更が不要ならPRに理由を一文記した。

- [ ] 追加した振る舞い・失敗時の扱いを該当する機能にまとめた。保証の欠落・重複がなく、共通制約の適用先と関連文書・テスト側の参照が一致している。

- [ ] 長期にわたって参照する判断理由がある場合だけADRを追加した。先行設計は対象版・重要な未実装差分・追跡先を示した。

- [ ] 内容を変えた文書の`updated`と必要な状態・indexのリンクを更新した。SPEC・GLOSSARYのActiveへの合意、ADRのAccepted・Rejectedへの確定は「プロジェクト設定」の方法で確認した。

- [ ] ADRのProposedでは判断日・判断者を省略し、Accepted・Rejectedへの確定時に記録した。本文の結論・理由を状態と揃え、不導入の方針への合意と提案の却下を区別した。

- [ ] 文書の作成・更新や記録対象の作業・判断にAIを利用した場合、対象文書の「AI利用記録」にモデル・関与範囲・役割を記し、人間側の責任と区別した。

- [ ] 検査コマンドが成功し、保証に影響する未決事項や実装との食い違いを隠していないことをレビューした。

判断の置換（通常の変更に追加）:

- [ ] 後継ADRに新IDを付けてAcceptedにし、旧ADRの当時の結論・理由・判断日・判断者を維持した。

- [ ] 新側の`supersedes`、旧側の`superseded_by`と`Superseded`状態を同じPRで更新した。

- [ ] 関連SPECと必要なindexのリンクを更新し、移行中なら適用時期・旧判断が残る範囲・移行の追跡先を示した。

担当交代:

- [ ] 後任と対象文書・未決事項・進行中の移行を確認した。後任未定なら「担当不在時の引き継ぎ先」が文書の管理窓口を担当した。

- [ ] 対象文書の`owners`と`updated`を更新した。過去のADRの`decision_makers`は当時の記録として維持した。

- [ ] 後任が文書を探せること、検査を実行できること、次の変更時の合意方法を確認した。

## 版と公開

通常はコードのリリースタグでdocsも参照し、文書ごとの`rev`は使わない。

SPECを別チームとの独立した契約として配布する場合だけ`rev`を導入し、互換性の意味を決める。
例: MAJORは既存の利用者または適合実装に影響する非互換、MINORは互換な追加、PATCHは要求する振る舞いを変えない修正。

これは仕様契約向けの運用規約であり、製品版やAPIのバージョンと自動的に同一にはしない。0.xは安定前として扱う。

文書別のタグ名を付けても、タグが示すのは文書単体でなくリポジトリの履歴上の時点である。

ADRやRESEARCHは原則Git履歴で管理し、独立したrevや変更履歴表を設けない。

## 閲覧・公開

Markdownを本文の正本とし、閲覧エンジンへ依存する記法は最小にする。

閲覧環境で対象のブランチ・タグ・コミットを判別できない場合は、`index.md`に対象版を1行で表示する。閲覧UIまたはビルドが自動表示する場合は追加記入しない。

`README.md`と`index.md`を別々の場所にも複製して更新する運用はしない。
閲覧方法が変わっても、規約はREADME、案内はindexという責務を保つ。

MDwikiを採用する場合は、`index.md`を本文、`index.html`を閲覧エンジンとして管理する構成とする。
採用する版でfront matter、相対リンク、アンカー、非公開ページの公開範囲を確認する。

メタデータをそのまま表示できない場合は、原本を変えずに表示用のコピーで整形する。

## 付録: 検査器のテスト

この付録は、検査ルールや検査スクリプトを保守する人向けの説明とする。

`check-docs`は文書を検査し、`run-tests`は検査器が期待どおりに動くかを確認する。テストの合格は、実プロジェクトの文書が合格したことを意味しない。

### テストの仕組み

PowerShell版とBash版のテストは、共通の[cases.tsv](scripts/tests/cases.tsv)を読む。TSVは、列をタブで区切ったテキスト形式であり、検査条件と期待する結果を記録する。

1. ケースごとに、一時フォルダーへ`examples/`とテスト用のindexをコピーする。

2. `cases.tsv`の指示に従い、コピーに文字列の置換・追記・ファイルの追加・削除等を行う。IDの重複やリンク切れなど、意図的に不正な文書も作る。

3. そのコピーに対して、同じOS向けの`check-docs`を通常モードで実行する。終了コードと、指定がある場合は出力に含まれる診断文を期待値と比較する。

4. ケースごとの結果と最後の集計を表示し、作成した一時フォルダーを終了時に削除する。元の完成例や実プロジェクトの文書は変更しない。プロセスの強制終了等では一時フォルダーが残る場合がある。

同じケース名の行は複数の操作を表し、まとめて1件のテストになる。例えば、不正な文書を作り、検査器が終了コード`1`と所定の診断文を返したなら、そのテストは合格となる。

PowerShell版の実行ではPowerShell版だけ、Bash版の実行ではBash版だけを検証する。検査ルールを変更した場合は、それぞれの環境で実行する。

### 結果の読み方

成功時の出力例（途中省略。件数はケースの追加・削除によって変わる）:

```text
PASS valid
PASS duplicate_doc
...
Tests: 40, failures: 0
```

- `PASS ケース名`: 終了コードと、指定された診断文が期待どおりだった。
- `Tests`: 実行したケース数。TSVの行数ではない。
- `failures: 0`: 全ケースが合格した。テストスクリプト自身の終了コードは`0`となる。

失敗時の出力例:

```text
FAIL duplicate_doc (expected 1, got 0):
OK: 4 documents, 0 errors (strict mode)
```

この例では「文書IDの重複をエラーにする」想定なのに検査器が成功したため、テストは失敗している。`expected`は期待する検査器の終了コード、`got`は実際の終了コードで、その下に実際の検査出力が続く。

終了コードが一致していても、指定された診断文が出力に含まれなければ`FAIL`になる。1件以上の不一致があれば、テストスクリプト自身は終了コード`1`を返す。

失敗時は、ケース名で`cases.tsv`を探し、操作内容・期待値と表示された検査出力を照合する。検査器の不具合か、意図した規則変更に伴うケースの修正漏れかを判断する。

最後の`Tests: ...`が出ずに停止した場合は、先に表示されたエラーを確認する。完成例の不足、置換対象の文字列の変更、実行環境の不足等により、テストの準備や実行が途中で止まった可能性がある。

### cases.tsvを更新するとき

普段の文書更新では編集不要とする。検査ルールの追加・変更や不具合修正時に、再発を検出できるケースを追加・調整する。

| 列 | 内容 |
|---|---|
| `case` | ケース名。同じケースの行は連続して置き、上から順に操作する。 |
| `exit` | 期待する検査器の終了コード。正常な文書は`0`、検出すべき文書エラーは`1`。 |
| `operation` | `noop`（変更なし）、`replace`（文字列置換）、`append`（追記）、`put`（ファイル作成・上書き）、`copy`（複製）、`remove`（削除）。操作は一時コピーにだけ適用する。 |
| `file` | 一時コピー内の対象ファイル。`@SPEC@`・`@ADR@`は完成例、`@SPEC2@`・`@ADR2@`は追加文書のパスを表す。 |
| `before` | `replace`で置換する文字列。使わない場合は`-`。 |
| `after` | 置換後・追記・作成する内容。`copy`では複製先のパス。使わない場合は`-`。 |
| `diagnostic` | 検査出力に含まれるべき文字列。照合不要なら`-`。 |

同じケースの`exit`と`diagnostic`は全行でそろえる。判定には最初の行の値を使う。

列区切りには実際のタブを使い、本文中の改行・タブは`\n`・`\t`と記述する。空行と行頭が`#`のコメント行は読み飛ばす。
